# КуМир за стеной

**Категория:** Web
**Сложность:** easy
**Флаг:** `SOLARCTF{n3_s0tv0r1_s3b3_kum1r4}` (отсылка к "не сотвори себе кумира", каламбур на слово "КуМир")

## Дано

Форум-страница "Клеточка" (`kumir-behind-the-wall.solarctf.ru`), под капотом gunicorn. Из docker-compose, который удалось посмотреть, видно топологию сети: публичный сервис `web` сидит сразу на двух сетях, `govnonet` (внутренняя) и `edge` (с выключенным masquerade, то есть без выхода в интернет снаружи), а вот сервис `kumir-checker` на порту 8081 висит только на внутренней `govnonet` и снаружи вообще не торчит.

Раз есть сервис, видимый только изнутри сети, значит нужен SSRF, чтобы до него дотянуться через сам `web`.

## Поиск SSRF

В профиле пользователя есть функция "аватар по ссылке": `POST /profile/avatar` с полем `avatar_url`. Сервер сам идет по этому URL, забирает содержимое и потом отдает его назад через `GET /api/avatar/me`, причем отдает как есть, без проверки content-type. Получается полноценный SSRF с чтением ответа, то есть можно подставить любой внутренний адрес и прочитать, что оттуда вернулось.

Небольшая техническая неприятность: ручки требуют сессионную куку, а curl на Windows не хотел нормально писать cookie jar по абсолютному пути вроде `/tmp/...`, помогло просто указать относительный путь в текущей директории.

## Разведка внутреннего сервиса

Через этот SSRF дергаю `kumir-checker` и смотрю на ответы, в том числе на диагностические 404. Из них становится понятен его API:

```
GET http://kumir-checker:8081/teacher/check?task=robot-final&answer=<строка>
```

Если ответ правильный, отдает `200 {"verdict": "OK"}`. Если неправильный, отдает `422` и вместе с ним отчет для препода, где по сути дублируется и присланный ответ, и то, что ожидалось:

```json
{"verdict": "WA", "expected": "SOLARCTF{...}", "received": "..."}
```

То есть сервис, который должен был быть скрыт за внутренней сетью и недоступен снаружи, при любом неправильном ответе сам прямо в JSON пишет правильный.

## Эксплойт

Одна-единственная SSRF-ссылка с заведомо неверным ответом:

```
avatar_url=http://kumir-checker:8081/teacher/check?task=robot-final&answer=test
```

(при отправке через curl внутренний `&` в параметре нужно кодировать через `--data-urlencode`, чтобы он не разорвал запрос раньше времени).

После этого идем на `GET /api/avatar/me` и в теле ответа лежит тот самый отчет с полем `expected`, где флаг.

## Вывод

Классический "SSRF до внутреннего сервиса", только добивающий удар был совсем простой: сервис для проверки ответов в отчете о неправильном ответе сам публикует правильный. Хватило одного неверного запроса через прокси из функции аватарки.
