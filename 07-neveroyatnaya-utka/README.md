# Невероятная утка

**Категория:** Reverse
**Сложность:** hard
**Флаг:** `SOLARCTF{unr34l_3ng1n3_p4th_f1nd1ng_0n_w1nd0ws}`

## Дано

Архив `unreal_duck.zip` с клиентом `UnrealDuckClient` на Unreal Engine 5.7. Игра мультиплеерная, с выделенным сервером, в лобби сидят еще живые игроки. По описанию: "в этой игре явно что-то скрыто, но что?"

## Разбор клиента

Клиентский exe зашит в формате IoStore (стандартная упаковка ассетов UE5), так что первым делом нужно было достать из него нормальные данные. Для этого взял `retoc`, он умеет распаковывать IoStore-контейнеры обратно в читаемый вид.

Дальше смотрел логику уже не через ассеты, а статическим реверсом самого exe. В качестве дизассемблера использовал `Instruction.parse` из Frida, им же проще было тыкаться по конкретным адресам, не поднимая полноценную IDA/Ghidra сессию под весь движковый бинарь.

В `UDuckGameInstance::Init` нашлись три захардкоженных route-записи (RouteId 0, 1, 2). Дальше прошелся по обработчику ввода: функция на `0x14438f5f0` слушает нажатия клавиш, и если игрок стоит внутри специального `SessionVolume` (триггер-зоны, привязанной к конкретному RouteId) с закрытым чатом, первые 5 введенных букв хешируются. Когда игрок выходит из зоны, вызывается `SendRouteFrame` (`0x14438b8a0`), который отправляет этот хеш на сервер через `ServerRecordFrame`.

Перебором (благо вариантов немного, уникальное решение на каждую зону) вытащил три правильных кода:

- route 0: `ILOVE`
- route 1: `DUCKS`
- route 2: `ALOTT`

В лобби были видны ники других игроков вида `SOLARCTF{ILOVEDUCKSA...}`, то есть народ буквально склеивал три кода подряд в фигурные скобки и пытался сдать это как флаг. В чате сами писали, что это не подходит. Это и есть красивый decoy: коды реальные, но сам флаг не является их конкатенацией, а выдается игрой отдельно после выполнения маршрута.

## Прохождение в игре

Дальше чистый reverse engineering закончился и начался геймплей. Зоны (`SessionVolume`) физически не отмечены на карте никак, нужно было ходить по уровню и попадать в нужные координаты, ориентируясь только на данные, вытащенные реверсом. Чтобы не бегать вслепую, собрал поверх игры небольшой оверлей с текущей позицией и статусом зон, который переводил нажатия стрелок в смещение по осям (вверх = +X, вправо = +Y) и показывал, в какой зоне стоишь и вышел ли из нее с отправленным кодом. Отсюда, собственно, и флаг про "path finding on Windows": без своей карты в чистом поле это было больше похоже на навигацию вслепую, чем на реверс.

По очереди заходил в каждую зону, печатал нужный код (не открывая чат), выходил из зоны, игра подтверждала, что код принят. После того как все три зоны отмечены как `OK`, у утки включается состояние "accent" (`SetAccentState`), и сервер пишет в общий чат что-то вроде "<Duck> completed the route and can head to the end".

После этого остается дойти до `DuckFinishBlock` (у него есть обработчик `HandleGoalOverlap`). При касании этого блока сервер шлет на клиент payload через `ClientReceivePayload`, и всплывает окно "Message received" с картинкой, на которой от руки написан флаг.

## Вывод

Задача честно разделена на две совершенно разные части: сначала статический реверс shipping-билда UE5 (распаковка IoStore, поиск обработчика ввода и сетевой отправки кода по адресам в дизассемблере), а потом живая навигация по игровому миру с ручным контролем позиции, потому что без координат по зонам просто не попасть. Ложный след с конкатенацией трех кодов в один флаг отсекался сразу, стоило дойти до реального финиша и получить картинку с сервера.
