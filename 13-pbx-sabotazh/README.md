# PBX-саботаж

**Категория:** Forensics
**Флаг:** `SOLARCTF{v0ip_c4ll_1nt3rc3pt3d}`

## Дано

Дамп `pbx_capture.pcapng` на 19 МБ, 61045 пакетов, 22 минуты трафика (05:00:15-05:22:35). Легенда: подрядчик дозвонился на сервисный добавочный АТС, передал код активации скрытой функции синхронизации, а потом слил бэкап конфигурации. Нужно восстановить, что именно утекло.

## Карта сети

`tshark -q -z io,phs` сразу показывает, что в дампе не только SIP, но и TFTP, HTTP, SMTP. По IP и SIP-заголовкам собирается картина: АТС `10.20.30.5` (Asterisk), восемь SIP-телефонов `10.20.30.101-116`, рабочая станция `10.20.30.77` и внешний хост `198.51.100.66`, который представляется как `svc-trunk` и держит одновременно почтовый сервер и сервер для аплоада. Три звонка с этого внешнего хоста идут на добавочный `108`.

## Первый слой: DTMF через RFC2833

Стандартный способ передать тоновый набор в SIP, события `telephone-event`, разбираются тривиально:

```bash
tshark -r pbx_capture.pcapng -Y rtpevent -T fields -e frame.time_relative -e rtp.ssrc -e rtpevent.event_id -e rtp.timestamp
```

После дедупликации событий по одинаковому `rtp.timestamp` (каждая цифра это несколько одинаковых пакетов подряд) получаются куски кода из первого и третьего звонка, 32 и 18 символов. Во втором звонке RFC2833 нет вообще. Алфавит кодов ровно `0123456789ABCD`, то есть `*` и `#` никогда не встречаются — это намекает, что генератор кода берёт полный 14-символьный "телефонный" алфавит. Прямой перебор PBKDF2/AES на этих кусках ничего не даёт: код неполный.

## Второй слой: тоны внутри самого аудио

Это и есть основная находка задачи. Wireshark показывает только events-канал, а DTMF можно ещё и просто наиграть внутри самого звука, в полезной нагрузке RTP (G.711/A-law). Чтобы найти, где это есть, считаем, сколько уникальных байт встречается в каждом RTP-потоке: у настоящего сигнала разброс большой, у синтетического шума (которым залиты остальные 30 потоков) почти постоянная амплитуда и всего около десятка уникальных значений.

Шесть "живых" потоков декодируются из A-law в линейный PCM и прогоняются алгоритмом Гёрцеля по восьми частотам стандартной DTMF-матрицы (697-941 Гц строки, 1209-1633 Гц столбцы). Энергия победившей частоты превосходит вторую больше чем в 300 раз, декод однозначный. Так находятся тоны второго и третьего звонка, а заодно отвлекающий тоновый набор во внутреннем звонке 115→116 уже после слива (не часть решения).

## Склейка кода

В третьем звонке RFC2833-события и внутриаудио-тоны идут не одновременно, а чередуются ровно по 4 символа с характерными паузами 1.78 с (внутри группы шаг 0.58 с). Переводим тоны в абсолютное время по меткам RTP-пакетов и сортируем вместе с событиями одного потока — получается идеальное чередование "4 цифры RFC2833 / 4 тона в аудио", и обе половинки третьего звонка склеиваются в один 34-символьный кусок.

Три куска (32 + 34 + 34 символа) перехлёстываются по два символа на стыке (последние два символа одного куска совпадают с первыми двумя следующего), что и выдаёт правильный порядок склейки без перебора:

```python
FULL = R1 + C2[2:] + M3[2:]
# 98B599B2CD56AC546B3CAD516DA618BA566CBC4A0D591732CD5AB9794C381A899C016A90A0A331437BC950C9569C380C
```

96 символов полного кода активации.

## Эксфильтрация: сразу три канала

Сразу после третьего звонка рабочая станция `10.20.30.77` начинает выгрузку на внешний хост тремя разными протоколами параллельно: TFTP (`pbx_backup.part1`), HTTP POST на `/u/upload.php` (`part2`), SMTP-вложение в письме `node.sync@mail.att-node.net` (`part3`). Каждый чанк начинается заголовком `SOLPBKCH` + индекс + общее число частей + длина + CRC32, все суммы сходятся. Склейка по индексу даёт 1868-байтный контейнер.

## Формат контейнера и расшифровка

Контейнер начинается с магии `SOLPBK01`, дальше версия, число итераций PBKDF2 (60000), 16-байтная соль, 16-байтный IV, длина шифротекста (1811, не кратна 16, то есть потоковый режим), CRC32 от открытого текста и сам шифротекст. Ключ для PBKDF2-HMAC-SHA256 это тот самый 96-символьный собранный код активации, шифр AES-256-CTR:

```python
import hashlib, struct, zlib
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

d = open('pbx_backup.solpbk', 'rb').read()
iters = struct.unpack('<I', d[9:13])[0]
salt, iv = d[13:29], d[29:45]
crc = struct.unpack('<I', d[53:57])[0]
ct = d[57:]

PW = '98B599B2CD56AC546B3CAD516DA618BA566CBC4A0D591732CD5AB9794C381A899C016A90A0A331437BC950C9569C380C'

key = hashlib.pbkdf2_hmac('sha256', PW.encode(), salt, iters, 32)
pt = Cipher(algorithms.AES(key), modes.CTR(iv)).decryptor().update(ct)
assert zlib.crc32(pt) & 0xffffffff == crc
```

CRC сходится, внутри лежит полный конфиг АТС `pbx_backup.conf`, а в свежей секции `[backup-v2]` прямым текстом:

```ini
[backup-v2]
kdf = pbkdf2-hmac-sha256
cipher = aes-256-ctr
secret_code = SOLARCTF{v0ip_c4ll_1nt3rc3pt3d}
```

## Отвлекающие манёвры

В дампе специально намешан шум: случайные HTTP-страницы, якобы обновление прошивки (900 КБ чистой энтропии, льётся уже после слива), гигабайты TLS-трафика, mDNS/NTP/ARP, внутренний DTMF-набор `105` (просто чей-то номер) и ещё один тоновый код уже после кражи данных. 30 из 36 RTP-потоков залиты синтетическим шумом ровно для того, чтобы шесть настоящих легко выделялись статистикой уникальных байт на фоне остальных.

## Вывод

Главный урок: один звонок редко означает один канал передачи DTMF. Wireshark из коробки видит только RFC2833, а тоны внутри самой аудиодорожки нужно искать руками через Гёрцеля, ориентируясь на статистические аномалии потоков. Второй урок: эксфильтрация размазана по трём независимым протоколам сразу, и если смотреть только на один (например, только SMTP), теряется две трети файла. Перехлёст кусков кода на 2 символа — чистая подсказка автора задания, как склеивать фрагменты без перебора.
