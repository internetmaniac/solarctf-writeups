# Пустота

**Категория:** Forensics
**Флаг:** `SOLARCTF{v01d_l1nuzz_yjs_cv3_buzzw0rd5}`

## Дано

Образ памяти Linux-машины (`memory.elf`, Void Linux 6.12). Задача на полный форензик-разбор: нужно вытащить скрытый процесс, расшифровать его кэш, восстановить удалённую историю совместного документа и в итоге достать зашифрованный архив с флагом. Всё решается офлайн по самому дампу, без запуска чего-либо из него.

## Восстановление памяти

Сначала руками восстанавливается трансляция виртуальных адресов в физические: таблицы страниц x86-64, DTB берётся из структуры ELF-заголовков дампа, физическая память читается по сегментам из `PT_LOAD`.

## Скрытый процесс

В памяти находится загруженный вредоносный модуль ядра `hwsens_aux.ko`, который прячет поток службы классическим трюком: отсоединяет его от списков процессов и меняет `exit_state`, так что обычные средства его не видят. По сохранившемуся указателю `task_struct` поток всё равно находится напрямую в памяти по адресу `0xffff8d69af086900`.

Внутри загруженного модуля лежит замаскированный "набор восстановления": 16-байтный секрет и текстовые метки `asrn-cache:` / `asrn-index:`, которые дальше используются как часть ключей шифрования. Маска на секрете снимается простым XOR-замесом с boot-nonce и LCG-состоянием (`s = s*1664525 + 1013904223 mod 2^32`).

## Кэш процесса: два настоящих фрагмента среди пяти ложных

В памяти процесса лежат семь похожих блоков, из которых только два реальных (остальные — ложные приманки). Настоящие проходят проверку по FNV-1a-хешу, зашитому в их собственном заголовке. После снятия XOR/LCG-маски (с учётом циклического сдвига, который тоже завязан на boot-nonce) получается шифротекст AES-256-GCM: ключ — `sha256("asrn-cache:" + secret_hex)`, первые 12 байт буфера — nonce, последние 16 — тег аутентификации. Тег проверяется успешно.

## Что внутри кэша

Расшифрованный кэш содержит: журнал атаки (человекочитаемое описание инцидента: RCE через `sync-api.jsp`, повышение привилегий через `asrn-restore --apply`, сокрытие потока, подмена адресата письма), исходную и поддельную записи некоего документного формата DLS3, и двухслойный зашифрованный конверт SND1.

## Восстановление рабочего окружения из page cache

Из страничного кэша конкретных inode восстанавливаются файлы рантайма совместного редактирования (движок на основе Yjs: `core.cjs`), база `journal.sqlite` с историей правок документа и `objects.bin` со снятыми снапшотами. Для `objects.bin` и исходных записей реализован обратный кодек трёхпроходного DLS3-формата (XOR-поток + перестановка 16-байтными блоками + второй XOR-поток, у каждого прохода свой LCG), все CRC32 используемых записей сходятся.

Важная ловушка задания: сопроводительный `FORMAT.txt` утверждает, что digest родительской записи в цепочке восстановления считается от результата записи, но на практике в реальных данных digest относится к **запечатанному DLS3-конверту родителя целиком**, а не к его распакованному содержимому. Если следовать документации буквально, цепочка не собирается.

## Историческая версия документа и вложенный ключ

Текущий Yjs-документ уже не содержит нужный текст, его удалили. Восстановление делается через применение сохранённых апдейтов (`updates.json` из `journal.sqlite`) к документу с `gc: false` (иначе удалённые операции вычищаются сборщиком мусора Yjs и теряются безвозвратно), а дальше берётся не текущее состояние, а исторический snapshot конкретной более ранней записи — именно он содержит правильные символы ключа из длинного 256-символьного текста. Текущий документ, попытки угадать подстроку фиксированной длины или использовать текущий укороченный ключ результата не дают.

Из найденного исторического ключа строится ключ для внешнего слоя SND1 (`sha256("asrn-wrap:" + wrap_session + secret_hex)`), а из содержимого внешнего слоя — ключ для внутреннего (`sha256(historical_dispatch.release_key)`). Оба тега AES-GCM успешно проверяются. Внутри — ZIP-архив с текстовым файлом флага.

## Вывод

Задача построена как цепочка зависимых друг от друга расшифровок: ядерный модуль прячет процесс, процесс прячет ключ, ключ открывает кэш, кэш содержит и журнал атаки, и зашифрованные записи документа, а сам документ нужно не просто прочитать, а восстановить в конкретной исторической версии через полноценный CRDT-движок, прежде чем из него добыть финальный ключ. Единственная задокументированная, но ложная деталь (к чему именно относится digest в цепочке) была специально расставленной ловушкой, отличающей формальное следование спецификации от проверки на реальных данных.
